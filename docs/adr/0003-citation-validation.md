# ADR-0003：引用验证分层与指标命名

| 项 | 内容 |
|---|---|
| 状态 | 已接受 |
| 日期 | 2026-10-19 |
| 决策者 | 项目组 |
| 相关文档 | [技术方案](../technical-plan.md) 第 4 节 D4、第 8、10 节 |

## 背景

旧方案用正则检查 `[k]` 是否在 Top-K 范围内，并把这称为“引用正确性验证”。该检查只能发现编造的编号，不能判断来源是否支持陈述。例如“南美白对虾适合在任意盐度环境中养殖。[1]”中 `[1]` 真实存在，但内容可能完全不支持该结论。

## 决策

分三层验证，指标分开命名：

| 层次 | 验证内容 | 方法 | 运行时机 |
|---|---|---|---|
| 引用有效性 | Source ID 是否存在、是否属于本次证据、版本是否有效 | 确定性程序 | 每次回答 |
| 引用支持性 | 来源是否支持对应陈述 | NLI/LLM + 人工复核 | 可选；实验重点 |
| 事实正确性 | 陈述是否符合领域知识与适用条件 | 参考答案、专家 | 离线评测 |

指标：

- **引用支持率** = 被引用的事实陈述中，来源确实支持的比例。
- **事实引用覆盖率** = 需要证据的事实陈述中，具有有效且可追溯引用的比例。

不使用未定义的 “Citation Precision / Recall”。

## 备选方案

| 方案 | 不采用的原因 |
|---|---|
| 仅正则校验编号 | 只能防编造，不能防“有效但不支持” |
| 全部交给 LLM 判断 | 成本高、延迟高、判断不稳定；不适合每次请求 |
| 只做人工评估 | 无法运行时提示，也无法规模化 |
| 直接叫 Citation Precision/Recall | 文献口径不一致，论文定义易被质疑 |

## 后果

- 运行时先做确定性校验，保证不出现不存在的 Source ID。
- 支持性验证作为可选步骤，记录额外延迟与成本，不阻塞流式输出。
- 论文必须同时报告支持率与覆盖率，并说明人工标注协议与 κ。
- `chat_citations.support_status` 保存 `valid` / `invalid` / `unverified`，便于统计。
- 高风险领域（用药、诊断）对“有效但不支持”更敏感，需人工抽查。
